# M1.3 — segmented construction

QUANTUM Dynamics can assign compatible construction variants to exact station
intervals on one immutable generated or imported track. This is construction
infrastructure and a development diagnostic, not a production construction editor.
Base: verified M1.2 `ff0130995e51db833948687d25ad6638fbadf658`.

## Assignment and boundary contract

`qx-style::construction_segments` separates a parent style, a registered variant
(with a validated existing construction definition), and a stable-ID station
assignment. `ConstructionMap` is renderer/document independent and serializable;
the diagnostic parser denies unknown fields and bounds input to 1 MiB / 1,024
segments. The map must cover **exactly** zero through the input track's final
station, with finite positive-length intervals. There is no uncovered default.

Validation sorts by start station then stable ID without changing the source
list. Repeated IDs, gaps, overlaps, unknown registrations and out-of-range/nonfinite
stations fail with contextual errors. Adjacent endpoints must be numerically
identical; there is no tolerance-based snapping. For imported NL2 data, the final
station must use the importer's reported `station_extent_m` round-trip value,
not a rounded kilometre length. Zero-length markers are unsupported.

Intervals are `[start_m,end_m)`. The next interval owns an internal boundary;
the last interval includes the final station. Binary search implements lookup.
A privately constructed `ValidatedConstructionMap` borrows both assignments and
definitions, preventing their mutation while validated results are in use.

M1.3 conservatively requires the same parent style and identical running sweeps
and strategy: count, gauge, profile, mounting offsets, orientation, cap/visibility
settings and material reference must match. Conflicting material definitions
under one slot ID also fail. Compatible-but-differently-encoded rails are not
automatically recognized. There is no interpolation of incompatible rail systems.

`construction::segmented::build` sweeps the rails **once over the exact original
sample sequence**. Their vertices, normals, UVs, station mappings, triangles,
caps and bounds equal the ordinary full-track engine. Construction boundaries add
no rail rings, internal rail caps, duplicate surfaces or UV restarts. This retains
the baseline's tessellation and sample accuracy rather than claiming an exact
continuous manufactured surface between imported samples.

Non-running sweeps use clipped *derived* sample slices. Existing samples are copied
exactly; a boundary between samples uses the existing Hermite-position/shortest-
slerp query. Identical adjacent definitions coalesce, avoiding redundant caps and
hardware. Every changed structural run terminates with caps at the cut plane;
the report and pink rectangle identify an explicit transition asset/specification
as required. Different structural cap cross-sections may intersect in that plane;
no joint/weld/adapter is fabricated and structural connectivity is unverified.
Original outer endpoint cap settings are preserved, including uncapped custom
definitions; only internal structural cuts force a provisional cap.
Runs below 1 micrometre are rejected by the mesh adapter with a clear error.

Repeat phase and endpoint margins remain global track stations, never reset per
Region or construction segment. Center ownership follows the interval rule.
Nearby transformed rigid hardware is tested against the structural cut planes;
hardware crossing a changed boundary is omitted and listed by ID/station rather
than clipped, stretched, duplicated, or repositioned. A local bounding sphere
limits those plane checks. This is local termination handling, not global solid
collision certification. No automatic structural clearance search is performed.

All parts share the existing aggregate limits (2 million vertices, 12 million
indices, 100,000 placed instances, 384 MiB estimated mesh storage). Omitted-hardware
diagnostics are separately capped at at most 100,000 entries. Counts/allocations
are checked; sample clipping uses binary searches and copies only the active run.
Construction-specific component bounds drive the existing mesh/scene fitting.

## Support references and persistence

`segmented::attachment_reference` exposes the known original track position/frame.
It explicitly rejects requests for unverified named connector hardware. Neither
variant invents a support mount offset. Existing native `Attachment::resolve`
still uses its original Region/fraction/offset. Imported XML supports, their
rigid beam solids and alignment residuals are unchanged. The five BROBDINGNAGIAN
connectors referring to absent track 1 remain unavailable; none is remapped.
Connector/foundation/flange limitations remain those documented in M1.2.

Ordinary project serialization, schema version, migration, history, native
construction settings, train dynamics and heartline solving are untouched.
Future native integration needs an additive per-coaster assignment list with
stable segment IDs, physical station ranges, style/variant IDs plus definition
revision references. Native saving must retain embedded/overridden definitions
and preserve unknown data according to the existing version policy. A schema
version/migration must convert the current single definition into one full-length
assignment without changing its settings. Length changes need an owner-approved
boundary anchoring/invalid-coverage policy, transactional commands, undo/redo,
cache invalidation and round-trip/compatibility fixtures. These are **not implemented**.

## Future Track Workspace proposal — not implemented or approved

An owner-designed extension could list independent construction intervals within
the existing Track Workspace, offer compatible variants for the selected style,
and provide precise start/end station entry. Selecting an interval could inspect
its boundary diagnostics and preview a reversible change using the existing
Apply/Cancel/history model. Region boundaries would remain independent. Boundary
anchoring during track edits, visual markers, keyboard commands, grouping and
selection gestures all require owner design. No production panel, dialog,
gesture, toolbar or automatic suggestion was added in M1.3.

## Verification and limitations

See the final verification record below and [the Rust/C++ lesson](m1.3-rust-guide.md).
Native GUI navigation/usability is **not manually verified**. Owner checklist:
run the synthetic command without `--render`; orbit/pan/zoom and F-fit; inspect
both boundaries and inverted geometry; toggle rails/structure/hardware/supports;
edit only a copied sidecar, Ctrl+R; introduce a gap and confirm the previous scene
remains with an error; Clear, reload, and close. Ordinary projects should still
save/reopen independently through the normal application launch.

Approved behavior followed: underlying station assignments, read-only developer
sidecar, existing viewer and offscreen evidence. Temporary UI: assignment text
and provisional boundary rectangles in that viewer only. Production construction
editing, transition hardware and final double-spine specifications need owner
design. No structural/safety certification or guaranteed frame rate is claimed.
